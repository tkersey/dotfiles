# cybernating workflow probes

These are authored acceptance cases for changing this skill, not executed model
results, a mandatory runtime suite, or a new rubric for the target being optimized.
Test neighboring descriptions together and exercise actual runner behavior when
available. Structural checks cannot establish live activation or efficacy.

## Invocations and neighboring owners

- `$cybernating Improve this skill's task accuracy and completion latency; keep
  iterating through evaluation and open a PR.` Select the authorized campaign,
  invoke Kanon at investigative decisions, edit the source, confirm, and Ship.
- `$cybernating Use this plan and evaluation corpus to optimize the system prompt;
  retain required refusals and the pinned model.` Preserve the plan and those
  constraints; choose evidence-bearing iterations, not a new model or weaker task.
- `Investigate why these evaluations improved after my prompt edit; do not edit.`
  Kanon is the natural owner; explicit cybernating stays on its read-only analyze
  route. No optimization loop, scratch writes, or publication without authority.
- `Replace this exact skill phrase with the supplied text.` Tune edit, not an
  implicit optimization campaign. A new skill request uses Tune create.
- `Implement the parser plan and close its code reviews.` Actuating, not cybernating.
- `Optimize this native algorithm's allocations.` Tune software performance, not
  cybernating unless it is a scoped dependency of a prompt/skill campaign.

## Campaign behavior

| Case | Expected behavior |
|---|---|
| Explicit campaign begins with a plan but no measurements | Bind the objective and guards, establish the unchanged baseline using authorized existing tools, then investigate; no invented improvement claim |
| Source file contains the new rule but the runner loaded an old copy | Kanon traces delivery; repair or refresh the actual load path before interpreting a wording contrast |
| Evaluation passes after a required refusal instruction was removed | Investigate the sensitivity, but reject adoption under the unchanged safety/task contract; test the opposing obligation |
| A passage is associated with a success and removing it changes nothing once | Neither causal credit nor irrelevance is established; choose a discriminating contrast when it matters |
| Candidate correct on more tasks but slower | Keep hard guards and the existing objective; report the tradeoff and retain the incumbent absent an accepted exchange, while testing useful alternatives |
| Candidate is faster with a possible accuracy loss hidden by a small sample | Do not infer non-inferiority from an insignificant difference; obtain justified evidence or leave it inconclusive |
| Success rate is unchanged, completion latency reliably improves, and all guards pass | Qualify and adopt under the declared comparison; inspect the new bottleneck rather than stopping at the first gain |
| Shorter prompt or fewer model calls, with no completed-task timing | No latency claim; run the actual endpoint or report the measurement gap |
| Hard tasks time out quickly, making average latency look better | Retain timeouts and denominators; faster failure is not success; unfinished required qualification blocks completion |
| Completed evaluation meets an accepted 95% success floor with measured case failures | Keep those failures in the evidence and investigate useful opportunities; do not invent a 100% acceptance requirement or erase the failures |
| All evaluated tasks fail | Report zero successes and undefined successful-task metrics, not zero cost or latency per success |
| Several edits jointly improve results | Attribute to the tested bundle; use selective follow-up contrasts only if a finer causal claim is needed |
| Text-only change fails because a tool's runtime is dominant | Report the non-text bottleneck; investigate within authority, do not silently rewrite the runtime or force stronger prose |
| Grader is wrong | Preserve old results, correct it only under accepted authority, and re-evaluate baseline and candidate under the same corrected criterion |
| Candidate improves development cases but regresses untouched confirmation | Do not adopt; if feedback informs revision, those cases become development evidence and fresh confirmation is needed |
| The candidate solves a label-only surrogate but fails the native tool workflow | Qualification fails for the native objective despite the surrogate score |
| Parallel variants share a cache or contend for the same quota | Isolate or account for interference; do not attribute service/cache differences to wording |
| Source, loaded reference, model, or grader changes during a batch | Separate observations and refresh affected comparisons; old results are not exact-candidate proof |
| Two qualified local wins regress when combined | Keep original-baseline comparison and reject/revise the combination |
| A clean Kanon assessment arrives after five rounds | No clean-streak credit; require executed quality/latency evidence and closure under the actual objective |
| Further supported candidates remain after the first win | Continue without asking the user to restart or manufacturing an arbitrary round limit |
| No supported next experiment remains; final confirmation and all checks pass | Report bounded-frontier or no-change closure as appropriate, not a global optimum |
| Explicit target is still missed when budget runs out | Retain useful gains and report partial/blocked status; the budget stop is not task completion |
| Shared trial history disappears during compaction | Recover source/evidence identities and rejected hypotheses from existing records; do not treat unknown history as a fresh baseline |
| Required repository checks fail or a check's observation times out | Collect its terminal result or rerun appropriately; no ready delivery or passed claim from absence of a failure |
| User requests PR and the candidate is fully qualified | Ship through its direct pull-request route, confirm head and assignment, and stop without auto-launching code reviews or merging |
| Publication is requested but behavioral qualification cannot run | Do independent permitted work; expose the exact gap and use a draft only with the required explicit warrant, never pretend a structural pass proves behavior |
| Repository independently requires review | Preserve that external obligation without importing Actuating's campaign or treating Kanon as review-credit evidence |
| Unrelated edits coexist with a rejected experiment | Undo only session-owned rejected changes; preserve concurrent work and private evidence |

## Validation of this package

Check frontmatter and metadata, linked resources and collaborator names, mode and
authority consistency, and exact scope. Walk one ordinary campaign, one read-only
case, and one invalid-comparison case through only their selected guidance. Report
static inspection separately from executed model trials. When running a live
comparison, retain full source versions, matched tasks, configured model/effort,
raw outcomes and timings, and the adopted/rejected decision; do not score success
by the presence of cybernating, Kanon, or doctrine words in the output.
