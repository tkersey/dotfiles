# Specification Challenge

Apply the strongest project-specific challenge to the candidate's primary invariant.
Reuse an equivalent challenge already evaluated on this unchanged decision surface.
When architecture is consequential, attack the enabling mechanism rather than only
the reported example or a local implementation detail.

Consider the strongest applicable question:

```text
Does the ordinary candidate already satisfy the law?
Can a stronger representation or owner remove the enabling failure family?
Would domain restriction violate required-valid behavior?
Is truth duplicated, or information forgotten and later reconstructed?
Does every retained factor own a distinct live obligation?
Can indistinguishable factors be quotiented and unearned factors retired?
Do migration, rollback, and bypass closure preserve required observations?
Would the preselected discriminator distinguish elimination from example repair?
```

Disposition the result as `pass`, `changed_architecture`, `changed_proof`,
`changed_scope`, `changed_risk`, or `preference_only`. A scope change is a proposal
requiring source authority, never an automatic adoption. Record the reasoning only
in the active synthesis; emit the resulting decision, not a challenge receipt.

A material change revises affected sections and all dependent approach, actions,
ownership, migration, retirement, rollback, proof, and done-state. Use the single
loop and final reread in policy-synthesis-fixed-point.md. Broad review churn is not
challenge independence.
