# Architectonic Doctrine Probe Cases

Use these probes to verify that `$logophile` selects `ARCHITECTONIC` for governing organization, preserves adjacent distinctions, and does not claim architecture-selection authority.

## Should trigger architectonic doctrine

### Rearchitecture and better abstractions

```text
What is a doctrine word for rearchitecting or finding better abstractions?
```

Expected:

- primary mode: `ARCHITECTONIC`;
- meaning: discover the organizing abstractions, boundaries, owners, and composition laws that make the system coherent as a whole;
- runtime activation: `OPERATE ARCHITECTONICALLY` or normal form `Operate architectonically.`;
- plain alternative: `Find the governing abstraction.`;
- artifact only when needed: Architectonic Map;
- do not equate architectonic with adding more architecture.

### Current decomposition is suspect

```text
The code keeps adding validators and correlation maps because the model forgets information. What doctrine should force a better architecture?
```

Expected:

- `architectonic` as the governing mode;
- companions may include `representation-shifting`, `canonicalizing`, `reconstitutive`, and `invariant-seeking`;
- identify forgotten information, current owner, required observations, and candidate representation;
- reject another validator or cache as the default answer;
- do not implement the architecture through `$logophile`.

### Better abstraction across a system boundary

```text
I need a doctrine stack for discovering the right abstraction across several services that duplicate truth.
```

Expected:

```text
ARCHITECTONIC -> FACTORIZING -> CANONICALIZING -> RECONSTITUTIVE
```

- name live obligations and required observations;
- expose duplicated or shadow truth;
- identify canonical owners;
- include a preservation or refinement relation;
- reject service-shaped factorization when the service boundaries are themselves accidental.

### Category-theoretic architecture

```text
I want the architecture to be chosen by a universal construction when the context justifies one.
```

Expected:

```text
ARCHITECTONIC -> UNIVERSALIZING -> CANONICALIZING -> RECONSTITUTIVE
```

- `architectonic` governs whole-system organization;
- `universalizing` adds the factorization and uniqueness burden;
- require an obstruction when no universal property is justified;
- do not use `universalizing` as a synonym for generic or reusable.

### Technical-debt rearchitecture

```text
The system has years of compatibility layers and helper abstractions. I want to recover the real structure and rebuild around it.
```

Expected:

```text
STRATIGRAPHIC -> ARCHITECTONIC -> FACTORIZING -> ABLATIVE -> NORMALIZING
```

- historical layers must retain their former obligations;
- architectonic selection must precede deletion;
- ablation removes only residue without a live obligation;
- normalizing recomposes the retained structure.

## Distinction probes

### Architectonic versus architectural

```text
Should the doctrine word be architectural or architectonic?
```

Expected:

- `architectural` is topical: it concerns architecture;
- `architectonic` is operational: it discovers or imposes governing organization;
- prefer `architectonic` for a doctrine mode;
- do not choose the rarer word when the task only labels a topic.

### Architectonic versus principal

```text
Is architectonic just another word for principal?
```

Expected:

- no;
- `architectonic`: governing organization of the whole relevant system or boundary;
- `principal`: most general solution satisfying constraints;
- a principal abstraction may be one candidate inside architectonic selection;
- artifact distinction: Architectonic Map versus Principal Solution and Instantiation Map.

### Architectonic versus reifying

```text
Is defunctionalizing callbacks architectonic or reifying?
```

Expected:

- `reifying` when the core move turns hidden behavior into explicit data;
- `architectonic` only when that move changes the governing organization, ownership, or composition of the system;
- valid stack when both apply:

```text
ARCHITECTONIC -> REIFYING -> ALGEBRAIC -> TOTALIZING
```

- do not use architectonic merely because the refactor is large.

### Architectonic versus factorizing

```text
I already know the governing abstraction but need to split it into independent factors. Which word?
```

Expected:

- `factorizing`;
- architectonic selection is already complete;
- require an explicit recomposition rule and coupling map;
- do not restart architecture search without evidence that the governing organization is wrong.

### Architectonic versus representation-shifting

```text
The owner boundary is correct, but the current data representation makes invariants impossible to express.
```

Expected:

- `representation-shifting` as the narrow primary operator;
- `architectonic` may be unnecessary;
- preserve the owner and composition structure unless evidence challenges them;
- require before/after observation preservation.

### Architectonic versus reconstitutive

```text
The architecture is selected. Now we need to rebuild the code around it.
```

Expected:

- `reconstitutive`;
- architecture selection is not reopened by default;
- `architectonic` names the prior selection posture;
- preserve the selected structure, retire superseded surfaces, and prove preservation/refinement.

### Architectonic versus morphogenetic

```text
We need to invent entirely new organizing forms before choosing one.
```

Expected:

```text
POIETIC -> MORPHOGENETIC -> ARCHITECTONIC -> ADJUDICATIVE
```

- `morphogenetic` generates new organizations;
- `architectonic` tests them against governing obligations;
- `adjudicative` selects using declared criteria;
- novelty receives no automatic preference.

## Behavioral-upgrade probes

### Formal term versus plain activation

```text
Replace “Find the governing abstraction” everywhere with “Operate architectonically.”
```

Expected:

- baseline is the incumbent;
- policy relation: likely refinement plus register shift;
- compare familiarity, decoding cost, cadence, task coverage, median, ceiling, and variance;
- verdict may be `specialize` or `benchmark`, not automatic `replace`;
- exact uppercase form may still be required by an established consumer contract.

### Retain local language

```text
The audience is nontechnical and the sentence only means “choose a cleaner design.” Should I use architectonic?
```

Expected:

- likely retain a plain phrase such as `choose a cleaner design` or `find the governing abstraction`;
- do not force `architectonic` when the register cost exceeds the precision gain;
- formal doctrine may remain internal.

## Should not trigger architectonic doctrine

### Local bug fix

```text
Fix this null check in the current owner without changing the abstraction.
```

Expected:

- no architectonic route;
- ordinary implementation/review workflow owns the task;
- `$logophile` may sharpen human-facing wording only if requested.

### File reshuffle

```text
Move these classes into a new folder and call it rearchitecture.
```

Expected:

- reject `architectonic` unless obligations, ownership, representation, or composition change materially;
- a file move is not a governing abstraction change;
- do not polish reorganization into rearchitecture.

### Architecture implementation request

```text
Implement the new module boundary and run the tests.
```

Expected:

- operational implementation request, not `$logophile` doctrine selection;
- do not execute through `$logophile`;
- use the owning implementation workflow.

### Over-abstraction

```text
Add interfaces and services for every concern so the design is more architectonic.
```

Expected:

- reject abstraction proliferation;
- each factor must own a distinct live obligation;
- conceptual compression, canonical ownership, and lawful composition matter more than layer count.

## Quality gate

An architectonic answer is ready only when:

1. `architectonic` is defined as governing organization, not architecture in general;
2. live obligations and required observations anchor the recommendation;
3. owners, factors, constructors/eliminators, and composition are considered;
4. accidental distinctions and shadow truth are challenged;
5. adjacent operators retain distinct jobs;
6. universalizing carries a real universal-property burden;
7. reconstitution follows selection rather than replacing it;
8. a local fix remains valid when rearchitecture is not warranted;
9. `$logophile` does not claim architecture-selection authority;
10. runtime activation remains terse and exact when a consumer contract requires it.
