# Codebase Doctrine

## Mission

Recover the repository's latent constitution and project only the doctrine that
will materially improve a named future consumer's decisions.

```text
evidence -> rival explanations -> governing pressures -> doctrine -> consumer projection
```

This is not quick onboarding, generic architecture description, or direct skill
authoring.

## Common path

1. Bind repository state, scope, target consumer, and the decision the doctrine
   must improve.
2. Inspect guidance, history, code paths, tests, failures, migrations, reviews,
   and proof surfaces before asserting a law.
3. Recover:
   - authority owners and boundaries;
   - governing laws and permitted variations;
   - historical wounds and the mechanisms that prevent recurrence;
   - proof obligations and accepted evidence;
   - unresolved but governed aporia.
4. Preserve rival models while the evidence is underdetermined.
5. Distinguish constitutional doctrine from conventions, implementation
   accidents, preferences, and obsolete history.
6. State each doctrine with scope, evidence, falsifier, exception authority, and
   consequence for future work.
7. Project the smallest task-relevant context for the named consumer; do not
   dump the whole atlas into every task.
8. Recommend a repository skill only when repeated future decisions need the
   doctrine and a narrower document or test cannot carry it.

Doctrine is useful only when it changes routing, ownership, proof, permitted
variation, or stopping.

## Progressive projection law

A durable doctrine atlas may be broad. Every consumer projection must be narrow:

```text
always disclose
  authority, laws, proof, and stop rules required for the current decision

conditionally disclose
  historical explanation, examples, exceptions, and specialist mechanics only
  when their triggering condition is live

never disclose by default
  unrelated atlas sections, worker prompts, raw chronology, and rival models
  already defeated for this scope
```

## Conditional disclosure

The complete pre-split contract is preserved byte-for-byte in
[FULL_CONTRACT.md](FULL_CONTRACT.md). Do not load it for one bounded doctrine
question or task projection.

Load it only for:

- full campaign modes and evidence ledgers;
- constitution, correctness-atlas, projection, or candidacy schemas;
- detailed historical-wound and aporia treatment;
- subagent policy, packet contracts, and fanout;
- Ledger persistence, refresh, audit, or supersession;
- an unported edge route.

Its frontmatter is archived source, not a second skill definition.

## Guardrails

- Do not infer a law from one rhyme or one ambiguous event.
- Do not convert current architecture into doctrine merely because it exists.
- Do not erase an unresolved rival model.
- Do not create process prose without an action-changing rule or proof.
- Do not let durable doctrine become always-loaded repository context.
