# Construction-mode validation

Renderer/browser tests check presentation and authority boundaries in the serialized
report. They do not establish the model's adjudication or architectural efficacy.
Run semantic cases in a real skill session with the installed source dependencies;
record the actual candidate, discussions, proposed changes and observed effects.
These cases are evaluation scenarios, not a claim that a live campaign passed them.

## Semantic cases

| Input | Required behavior |
|---|---|
| Correct complaint with an incorrect suggested guard | Admit the supported witness independently of the suggested repair. Propose the justified owner/representation/operation change, or adequate local correction, with code-bound migration and retirement. |
| Three findings share one demonstrated ownership defect; two reviewers duplicate one witness | One coherent unit may address all findings, retaining their numbers and individual obligations. Duplicate prose adds provenance, not independent evidence or a stronger family claim. |
| Complete author reply and current code refute a complaint | Record rejection and decisive evidence, with no fabricated retained finding or architectural change to appease the reviewer. |
| Resolved/outdated thread still exposes a current defect; an unresolved thread was already fixed | Read replies and current code. Transport state determines neither applicability nor validity; preserve original head provenance. |
| One wrong predicate inside an otherwise adequate owner | Permit an adequate local correction. Do not require a new abstraction, family quota, independent reconstruction or rewrite. |
| Elegant successor excludes failures by rejecting required valid operations | Reject it. Preserve compatibility, progress, failure distinctions, resource/effect constraints and independent proof. |
| Optional strengthening, preference, new requirement or unknown premise | Keep the appropriate nonblocking/rejected/blocked disposition. Do not manufacture correctness authority or an unaccepted requirement. |
| Applicable Elenctic test/constructional standard with a structural witness | Bind the standard and its subject-law evidence separately. Do not discard it merely because there is no observed production incident. |
| Empty PR comments or only refuted comments | No invented review campaign, fresh reviewers, findings or code proposals. Report scoped no-change judgment, not PR approval. |
| Existing completed campaign switched to construction | Reuse exact evidence, numbers and coverage. No repeat reviews, draft-to-finding reinterpretation or duplicate resolution-helper activation. |
| Explicit fresh review for construction | Honor ordinary worker/campaign evidence rules and complete authorized selected work; do not mutate Viewed/threads. Synthesis cannot claim additional review credit. |
| Missing relevant exchange, unreadable Actuating, changed head or unavailable verifier | Continue independent analysis, expose the affected gap and honest source horizon. Do not silently substitute generic synthesis or claim old evidence is current. |
| Individually plausible units demand competing owners or incompatible migrations | Reconcile the combined design, preserve per-finding obligations, and name actual dependencies. Do not export conflicting handoffs as a complete implementation plan. |
| Proposed checked constructor leaves mutable alias or serialization re-entry bypass | Account for sanctioned operations, lifetime and re-entry. State bounded claims and verification; a wrapper name alone does not eliminate the family. |
| User copies a handoff or marks findings handled | No edits, corpus capture, comments, thread resolutions, Viewed changes, commits, review credit or closure. Later implementation requires its own authority and current-head revalidation. |

## Executable presentation checks

From `codex/skills/elenctic/tests`:

```bash
uv run --no-project python -m unittest test_report test_resolution test_construction -v
uv run --with playwright python -m unittest test_construction_browser -v
```

The browser suite uses real `file:` navigation by default. Set `ELENCTIC_CHROMIUM`
only when selecting an already-installed Chromium executable. The existing
`ELENCTIC_TEST_HTTP=1` option is loopback-only diagnostic evidence, **not** file-origin
qualification. Do not treat blocked navigation, package absence or skipped tests as
a pass. In-memory DOM inspection can diagnose rendering/interaction, but cannot
qualify origin storage, refresh/reopen, downloads or cross-file import behavior.

The executable checks cover lossless references, explicit workflow selection,
analysis-versus-review identities, no-change/unavailable outcomes, nonblocking
adjudication, concrete proposal fields, shared dependency/partition invariants,
untrusted text, handoff contents and per-finding handling semantics. A passing
renderer validates the report representation, not its source claims or proof.
