# PR feedback to construction proposals

This is a proposal-only composition with the installed `$actuating analyze`, not
another reviewer, patch scheduler, or implementation loop. SKILL.md owns selection
and the narrower effect authority. Do not invoke bare Actuating, `implement`,
`review-closeout`, Ship, CAS reviews, or corpus capture through this route.

## Select evidence before campaign preflight

`for construction` uses an established, explicitly supplied Elenctic campaign's
full reconciled findings when available. Otherwise it analyzes existing PR feedback.
An explicit fresh-review request, such as `review for construction`, runs the
ordinary campaign first, under construction's no-GitHub-mutation limit. Do not infer
fresh review from PR authorship or start one merely to manufacture new comments.

For an existing or requested campaign, preserve its actual selection, frozen policy,
review evidence and coverage. Finish authorized runnable selected work before final
synthesis. Do not rerun complete reviews, substitute coordinator analysis for worker
coverage, or award Actuating review credit. A workflow switch is not a new epoch.

For feedback-only analysis, resolve the unique open PR under SKILL.md and bind its
repository, PR URL/number, base tip, review merge base and exact head. Inspect complete
relevant review threads and replies, review summaries and PR comments, including
resolved/outdated discussions when relevant. Follow the discovery and counter-case
rules in [prior-review-threads.md](prior-review-threads.md), but do not run its
resolution mutations or the campaign's Viewed selection, seed or worker machinery.
Retain source IDs/URLs, original subjects, observed discussion state and material
missing pages/exchanges. Resolved, outdated or author agreement is not adjudication.
The author's strongest substantive response is evidence, not an optional footnote.

Read the current code, requirements and causal paths needed to decide the feedback,
including unchanged dependencies and companion edits. Do not widen this to an
unrequested whole-PR audit. Record the inspected source horizon and gaps; an empty
feedback set is not approval. Allocate an actual opaque analysis ID in the existing
working set. A feedback analysis uses `elenctic-construction-identity/v1` with
`mode: analysis`, not an invented review campaign or a review verdict.

## Compose once over full evidence

Resolve Actuating and its selected dependencies from the actual installed skills
root recorded at invocation, not a lookalike in the reviewed repository. A frozen
Elenctic bundle contains auxiliary review questions, not the full Actuating runtime.
Read the actual Actuating entrypoint and follow its `analyze` route, including its
selected counterexample and architecture guidance before governed decisions. Record
the observed source paths/content identities in the existing working set; do not
modify the frozen review seed or policy to inject this later analysis.

Supply the accepted source obligations, compatibility and non-goals, authorized path
scope, exact candidate, full findings and counterevidence, prior discussions and
applicable verification. Include Elenctic's governing engineering standards with
subject evidence establishing their applicability; do not demote an applicable
standard to a reviewer's preference or invent subject laws from that standard.
Comment drafts are lossy presentation, not the input representation. Existing drafts
remain available; producing new drafts is not a prerequisite for this mode.

Actuating owns causal explanation and construction selection. Review Fold owns
law authority, validity and applicability, with `corpus_write_authorized: false` on
every handoff. Reuse adequate current adjudications rather than adding a ceremonial
second review. Separate the reported claim, established fact, current liability and
suggested repair. Accepting a complaint does not accept its fix; duplicate reports
add provenance, not independent witnesses. Reject refuted claims, retain optional
follow-ups as optional, and expose decision-relevant unknowns without inventing code
changes. Preserve every substantive feedback item's disposition and decisive basis
in the existing report, including feedback that produces no retained finding.

Use Actuating's architecture guidance for the supported failure mechanism and its
smallest adequate construction, not the smallest diff or a compulsory redesign.
Glaze, Metanoetic, Universalist and Reduce participate through Actuating's own
triggers and authority; do not first run resolution-mode synthesis or copy their
doctrine here. A source-bound local correction, deletion, adequate incumbent or
corrected explanation can be the right result. Architectural inquiry must preserve
required-valid behavior, compatibility and independent verification.

If analysis discovers counterevidence that changes a campaign finding, return it to
ordinary reconciliation before regenerating the proposal. Do not silently reclassify
findings in presentation, suppress blockers, or relabel optional work as a merge gate.
Unavailable helpers or evidence block only dependent decisions; never claim a generic
substitute is Actuating analysis. Deliver supported evidence with the actual gap.

## Deliver code-bound units, not instructions to rediscover the design

Reuse [resolution.md](resolution.md)'s canonical finding-number and stable R-unit
identity rules, lossless membership and per-finding satisfaction evidence. Its
Glaze/Metanoetic synthesis and draft-derivation sequence do not run in this route.
Every retained finding belongs to exactly one unit; all original evidence,
dispositions, uncertainty and eligible existing drafts remain available. Number new
findings once, preserve established numbers and withdrawn-number history, and never
use comment array positions as identity. Rejected comments belong in adjudication
outcomes, not fake findings or mandatory repair units.

A selected proposal must name actual repository-relative paths and symbols, the
replacement contract or operation, and the explicit changes to producers, consumers,
transitions and bypasses. Include the supported mechanism and why the proposed
construction would exclude it, valid behavior to preserve, migrations, displaced
code to retire (or why none), the discriminator and repository-native verification,
and material limitations. A compact before/after API sketch or proposed diff is
useful when it makes the change unambiguous; a speculative full patch is not required.
"Centralize ownership" or "improve the state model" alone is not a construction.

Use the existing group's objective/completion evidence for required constraints and
per-finding obligations. Optional members stay optional. Check all selected units
together for incompatible owners, contracts, migrations or duplicate implementations;
reconcile conflicts and express only real acyclic dependencies. Record that compact
cross-proposal compatibility judgment, not another review lane or decision store.

Each unit's proposal is one of:

- `proposed`: concrete changes and the complete intended construction argument.
- `preserve-incumbent`: supported no-change judgment with its basis; cannot discharge
  a retained blocker. Reconcile a refuted blocker first.
- `unresolved`: name the missing decision/evidence and next discriminator; no selected
  code change. Incomparable adequate candidates remain unresolved, not obstructed.
- `obstructed`: a supported, claim-scoped obstruction with its basis and reopening
  condition under Actuating's rules, not merely an unavailable tool or failed attempt.

A complete synthesis accounts for all retained findings and feedback; it can contain
explicit unresolved units. It does not mean implementation complete. A proposal is
neither a verified fix nor a family-elimination result. State the declared domain,
assumptions, unexecuted checks and residuals; distinguish intended exclusion from
containment and from proof on actual successor code. Do not weaken requirements or
assert universal exclusion from samples, type names or a green existing suite.

## Recovery and delivery

Use [html-report.md](html-report.md)'s construction result and shared offline report.
Preserve the original findings view, adjudication outcomes, concrete proposals,
copyable handoffs and per-finding handling state. Checks/notes are user handling,
not verified fixes, accepted designs or authority to implement. Copying grants no
source mutation, publication or merge authority; a later task must obtain authority
and revalidate the exact code before execution. Text-only still permits proposals
without artifact writes. Neither analysis nor its helpers persist a corpus or store.

Resume only the established analysis/campaign for the same PR, retaining its ID,
source horizon, source identities, numbering and existing report path. Refresh the
exact head/base and relevant complete discussions before synthesis and delivery.
Material discussion or source changes require affected adjudication/synthesis to be
refreshed, not a new review merely for a changed output label. A changed PR epoch
makes old evidence historical: preserve provenance, rebind through an explicit
restart/resume decision, and use a fresh identity and handling namespace. A switch
from standalone analysis to a requested review creates a real campaign; it cannot
inherit file coverage or handled state from comment analysis.

If final identity/discussion freshness cannot be established, disclose the stale or
incomplete horizon; do not deliver old proposals as current-head recommendations.
Synthesis unavailability preserves the evidence with `status: unavailable` and an
actual reason, rather than partial groups advertised as complete. A comment-only
analysis ends with its scoped construction judgment and outstanding decisions,
never APPROVE/BLOCKED/INCOMPLETE as a campaign verdict. A real campaign preserves its
actual review verdict independently of proposal availability. Link the verified
report path before the final high-value judgment; artifact failure does not suppress
the text. Semantic evaluation cases are in
[construction-validation.md](../tests/construction-validation.md).
